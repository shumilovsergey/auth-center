# auth-miniapp

Telegram-ветка auth-center без бота и без webhook, а заодно — парадная дверь в экосистему для того, кто зашёл в мини-апп сам. Мини-апп открывается внутри Telegram, проверяет подпись `initData` по `BOT_TOKEN` и сообщает личность в auth-center — тот привязывает её к сессии, которую браузерная вкладка уже опрашивает на `/poll`.

Вырос из [poc-telegram-app](/poc-telegram-app/README.md), где проверялась сама возможность: подпись сходится, а `start_param` из ссылки покрыт этой подписью.

```
вкладка браузера ──POST /qr-session──> auth-center            (сессия, токен)
       │                                    ▲
       │ ссылка t.me/<bot>/<app>?startapp=<токен>
       ▼                                    │
   Telegram ──> auth-miniapp ──POST /miniapp/auth──┘          (личность → сессия)
       │              (проверка HMAC)
       ▼
  WebApp.close()

вкладка ──GET /poll/{токен}──> code ──> redirect?code=…
```

## Чем отличается от прежней схемы с ботом

Раньше пользователь жал кнопку, попадал в чат с ботом, слал `/start <токен>`, и Telegram доставлял апдейт на `POST /webhook` — напрямую или через auth-proxy, если VPS не видел Telegram. Личность приезжала из тела апдейта; подробности — [`auth-center/tools/old_bot_auth.md`](/auth-center/tools/old_bot_auth.md).

Переписки с ботом больше нет: личность приходит из `initData`, подписанной `BOT_TOKEN`. Webhook и proxy **входу** не нужны, исходящего трафика к Telegram он не требует вообще. Код бота из auth-center удалён.

Вебхук в этом сервисе всё же есть — необязательный и ко входу отношения не имеющий: см. [«Бот-половина»](#бот-половина-app_url). По умолчанию он выключен, и тогда всё сказанное выше верно буквально.

Остальная половина протокола не менялась: `/poll`, одноразовый код, `POST /exchange`. Клиентские приложения ничего не заметили — `method` остаётся `telegram`.

## Переменные окружения

| Переменная | Обязательно | Описание |
|---|:---:|---|
| `BOT_TOKEN` | да | Токен бота от @BotFather. **Того же бота, что у auth-center** — из него обе стороны выводят общий секрет. Без токена приложение не стартует |
| `AUTH_INTERNAL` | да | Базовый URL auth-center, без пути. На одном хосте — `http://localhost:8886`, вызов не выходит наружу. На разных — публичный `https://…`, **обязательно https**: в теле запроса едет общий секрет |
| `APP_URL` | | Публичный базовый URL **этого** приложения, без пути. Задан — при старте вешается Telegram-вебхук и включается бот-половина (см. ниже). Пуст — маршрута нет, исходящих вызовов к Telegram нет, вход работает как раньше |
| `APP_NAME` | | Имя приложения: баннер `--version` и строка лога `start app=…` |
| `PORT` | | Порт сервера (по умолчанию `8892`) |

`BOT_TOKEN` и `AUTH_INTERNAL` проверяются при старте, а не при первом запросе: приложение, поднявшееся без них, выглядит здоровым и падает ровно в тот момент, когда кто-то пытается войти.

Базы данных нет.

## Маршруты

| Маршрут | Описание |
|---|---|
| `GET /` | Страница мини-аппа |
| `POST /api/auth` | `{"init_data": "<WebApp.initData>"}` → проверка подписи → флаг и токен сессии из `start_param` → вызов auth-center. Пустой `start_param` — это гость, см. «Парадная дверь» |
| `POST /webhook` | Апдейты от Telegram. Регистрируется, **только** если задан `APP_URL` — иначе маршрута не существует. См. «Бот-половина» |

Ответ:

```json
{"ok": true, "user_id": 507717647, "name": "Сергей Шумилов",
 "username": "sergey_showmelove", "redirect": "https://auth.sh-development.ru/",
 "code": "<одноразовый код>"}
```

`redirect` и `code` — путь назад: адрес приложения плюс код, выписанный **этой странице отдельно**. Кнопка склеивает их в `redirect?code=…` и уводит туда пользователя. При входе по QR `code` не приходит — см. ниже.

Код именно второй, не тот, что лежит в сессии: тот ждёт вкладка на `/poll` и потратит его, а одноразовый код, потраченный дважды, у кого-то не сработает. Два кода на одну проверенную личность ничего не раскрывают — каждый одноразовый, каждый живёт 60 секунд, и погасить любой всё равно можно только с `app_token`.

Ошибки — `{"ok": false, "error": "…"}`. Коды: `401` подпись не сошлась, `400` нет `initData` или в ссылке не было сессии, `502` auth-center отказал или недоступен (его формулировка передаётся как есть).

## Доверие между сервисами

auth-miniapp проверяет `initData` сам, значит `BOT_TOKEN` у него уже есть — тот же, что у auth-center. Вместо того чтобы заводить отдельный `APP_TOKEN`, обе стороны выводят из токена одно значение:

```
secret = hex(HMAC_SHA256(key=BOT_TOKEN, data="auth-center/miniapp/v1"))
```

Сам токен по проводу не ходит — это полный доступ к боту, и в теле каждого запроса ему делать нечего. Сравнение через `hmac.Equal`.

Значение выводится независимо с двух сторон и никогда не передаётся, поэтому расхождение никак не проявится в рантайме — auth-center просто ответит `403`, и вход сломается без объяснений. От этого страхует пара тестов с одной и той же фикстурой: `build/authcenter_test.go` здесь и `build/miniapp_test.go` в auth-center. Меняешь строку назначения или способ вывода — один из них падает и называет расхождение.

## Проверка подписи

Алгоритм из [документации Telegram](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app), `build/telegram.go` перенесён из PoC вместе с тестами:

```
secret_key = HMAC_SHA256(key="WebAppData", data=<bot_token>)
hash       = HMAC_SHA256(key=secret_key, data=<data_check_string>)
```

Проверяется и свежесть `auth_date` (не старше 24 часов).

Главное здесь — `start_param`. Значение `?startapp=` из ссылки входит в подписанные данные, поэтому ни токен сессии, ни флаг источника нельзя подменить по дороге, не сломав подпись. Тест `TestStartParamIsCoveredByTheSignature`.

```bash
cd build && go test ./...
```

## Локальная разработка

```bash
cd auth-miniapp
cp .env.example .env   # заполнить BOT_TOKEN и AUTH_INTERNAL
docker-compose -f dev-compose.yml up --build
```

Порт `8892`. В обычном браузере страница честно скажет, что не видит Telegram — реально проверять только через Telegram по HTTPS.

## Сборка продакшн-бинаря (linux/amd64)

```bash
cd auth-miniapp
docker-compose -f prod-compose.yml run --rm release
```

Бинарь окажется в `bin/auth-miniapp`.

## Деплой

1. Скопировать `bin/example.auth-miniapp.service` в `/etc/systemd/system/auth-miniapp.service`, заполнить `ExecStart=`, `WorkingDirectory=`, `BOT_TOKEN=`, `AUTH_INTERNAL=`.
2. `systemctl daemon-reload && systemctl enable --now auth-miniapp`
3. nginx на домен мини-аппа → `http://127.0.0.1:8892`, сертификат через certbot. **Telegram открывает мини-аппы только по HTTPS с валидным сертификатом.**
4. @BotFather → `/newapp` на боте auth-center → указать этот домен и `app_short_name`.

## Ссылка

```
https://t.me/<bot>/<app_short_name>?startapp=<токен сессии>
```

Токен сессии — то, что `POST /qr-session` возвращает в поле `token`: 43 символа из `A-Za-z0-9-_`, в `startapp` помещается без кодирования.

Пока кнопка в auth-center на неё не переведена, ссылка собирается руками — см. ниже.

## Проверка цепочки

Сессию можно завести curl'ом и открыть ссылку с полученным токеном:

```bash
TOKEN=$(curl -s -X POST https://auth-center.sh-development.ru/qr-session \
  -H 'Content-Type: application/json' \
  -d '{"redirect":"https://auth-client.sh-development.ru/callback"}' | jq -r .token)

echo "https://t.me/<bot>/<app>?startapp=$TOKEN"

# пока открываешь ссылку в телефоне — смотреть, как сессия меняет статус
watch -n1 "curl -s https://auth-center.sh-development.ru/poll/$TOKEN"
```

Ожидаемое: `pending` → `authenticated` с `code` и `redirect`, в логе auth-miniapp строка `auth: BOUND uid=… session=…`, в логе auth-center — `miniapp uid=…`. Сессия живёт 5 минут.

У страницы ровно два исхода, и оба выглядят как страница входа auth-center: та же палитра, та же карточка, рамка со значением и одна большая кнопка под ней — по высоте как плашка выбора провайдера (5rem, 80 px).

- **вошёл** — подпись «Вы вошли как:», под ней в рамке имя (нет имени — `@username`, нет и его — `id ‹номер›`), под рамкой кнопка «ДАЛЕЕ»;
- **не вошёл** — «Ошибка. Попробуйте снова» красной рамкой, тихой строкой техническая причина, кнопка «НАЗАД», которая перезагружает страницу и начинает вход заново.

Имя обрезается до 32 символов с многоточием: длинное имя перенеслось бы на вторую строку и подвинуло кнопку. Раньше предел был 24 — в рамке вместе с именем ехало «привет, ». Подпись переехала на отдельную строку и вернула имени всю ширину.

Имя — самое яркое на карточке (1.3rem, `--ink`): это единственное место, где человеку говорят, какой именно аккаунт вошёл, а на телефоне с двумя аккаунтами вопрос не риторический. Подпись над ним набрана ровно как «Войти через» на экране auth-center — два экрана идут подряд и должны открываться одной интонацией.

Цветом окрашен только отказ. Успех не красится в зелёный намеренно: auth-center молчит цветом, пока всё идёт нормально, и зелёная карточка звучала громче оригинала.

Причина отказа не переводится: её читает не пользователь, а тот, кому он пришлёт скриншот. Отказ страница никогда не убирает сама: исчезнувшую ошибку невозможно сфотографировать.

### Что страница делает сама

Страница знает адрес возврата в тот же момент, когда печатает приветствие, и на телефоне пробует уйти туда сама — через `AUTO_DELAY_MS` (450 мс).

Кнопки в эту секунду на экране нет: вместо неё крутится индикатор. Если переход состоится — а он почти всегда состоится, `location.href` внутри webview выполняется, — кнопку никто не увидит вовсе, документ снесут раньше. Показывать её ради этого промежутка значит показать человеку элемент, который мигнул и пропал: выглядит так, будто он не успел нажать, хотя нажимать было нечего. Индикатор в этот же момент говорит правду — страница уходит.

Через `MOBILE_ACTION_MS` (1 с) индикатор уступает место кнопке. Это страховка: клиент вправе не выполнить переход, а вечно крутящийся индикатор хуже кнопки, которую он заменил. Индикатор стоит в том же боксе (5rem), что и кнопка, поэтому подмена ничего не двигает.

На десктопе автоматики нет вовсе. Выход туда — `WebApp.openLink()`, а на браузерных клиентах Telegram (`weba`, `webk`, `web`) этот вызов сводится к `window.open`, который без пользовательского жеста ловят блокировщики. Заблокированный `window.open` выглядит со стороны страницы точно так же, как удавшийся, — проверить нечего, закрываться не на что. Клик кнопки этот жест приносит, и на десктопе он остаётся единственным маршрутом.

Что пробует каждый исход и что остаётся, когда попытка не прошла:

| Исход | Что делает сама | Закрывается ли | Что останется при отказе |
|---|---|:---:|---|
| телефон и любая неизвестная платформа | индикатор, `location.href` на `redirect?code=…` | да, из `pagehide` | через 1 с индикатор сменится кнопкой «ДАЛЕЕ» |
| `tdesktop`, `macos`, `weba`, `webk`, `web` | ничего — кнопка сразу, без индикатора | после нажатия, через `DESKTOP_CLOSE_MS` | — |
| QR | `close()` через `QR_CLOSE_MS` | да | «Вы вошли как: ‹имя›», без кнопки |

Про закрытие на телефоне: если навигация прошла, документ сносится, и `pagehide` — единственное доказательство, что переход состоялся, и последний момент, когда можно ещё что-то выполнить. Поэтому `close()` живёт там, а не в таймере: таймер вместе с документом и умрёт. Событие позже `AUTO_PAGEHIDE_MS` (3 с) уже не считается — это пользователь ушёл сам, кнопкой или свернув Telegram, и убирать за ним не наше дело.

Само закрытие после перехода — единственное место, где удобство куплено за надёжность: `close()` ложится поверх страницы, на которую только что перешли. Вынесено в константы `AUTO_*` в начале `script.js`, так что выключается, не трогая логику.

### Куда ведёт «ДАЛЕЕ»

Зависит от клиента — `WebApp.platform`:

| Клиент | Куда | Закрывается ли мини-апп | Почему |
|---|---|:---:|---|
| `tdesktop`, `macos`, `weba`, `webk`, `web` | внешний браузер, `WebApp.openLink()` | нет | у пользователя приложение уже открыто в настоящем браузере; оставить его во встроенном — значит развести две копии по двум местам |
| всё остальное | этот же webview, `location.href` | нет | телефон уже внутри Telegram, и `openLink` выбросил бы его в Safari или Chrome — наружу из приложения, откуда он пришёл |

Деление именно «десктоп против всего остального», а не «десктоп против мобильных»: неизвестная платформа скорее окажется новым мобильным клиентом, чем новым десктопным, и ошибка в эту сторону ничего не стоит — ссылка, открытая на месте, работает всегда.

На десктопе нажатая кнопка закрывает мини-апп — через `DESKTOP_CLOSE_MS` (1.5 с) после `openLink()`. Это не уборка за собой: **оставленный открытым мини-апп Telegram при следующем обращении продолжает, а не начинает заново** — пользователь просит новый вход и получает доевший своё экран прошлого. Закрытие ставит точку. Полторы секунды — чтобы `close()` не лёг поверх диалога «открыть ссылку?», который некоторые клиенты показывают на `openLink`: закрытие поверх него отменило бы ровно ту ссылку, которую мы только что отдали.

На телефоне нажатая кнопка не закрывает ничего: она меняет `location` этого же webview, и `close()` снёс бы страницу, на которую только что перешли. Автоматический переход закрывает — но там закрытие висит на `pagehide`, то есть уже после того, как переход состоялся.

Кнопка меняет `location` самого webview, а **не** зовёт `WebApp.openLink()`, когда клиент мобильный. `openLink` по документации Telegram открывает внешний браузер — и открывает: пользователь оказывается в Safari или Chrome, вообще за пределами Telegram. Это хуже свёрнутой вкладки, которую кнопка чинит. Навигация webview — единственный способ остаться внутри.

Плата за это: webview мини-аппа может не разделять куки с встроенным браузером, поэтому на сессию, которую только что завела вкладка, полагаться нельзя. Ровно поэтому в ссылке едет собственный код — приложение залогинит пользователя на входе, независимо от кук.

### Когда кнопки «ДАЛЕЕ» нет

Если пользователь пришёл по QR, кнопки не будет — только «Вы вошли как: ‹имя›». Карточка держится `QR_CLOSE_MS` (1.6 с), и мини-апп закрывается сам. Если клиент закрытие проигнорирует, на экране останется имя — ровно то, ради чего этот исход и существует, так что чинить там нечего.

> Кнопка при этом должна отсутствовать, а не быть пустой. До правки в CSS она оставалась на месте пустым прямоугольником в 80 px: `.action-btn[hidden] { display: none }` и `.action-btn.tall { display: flex }` имеют одинаковую специфичность, и побеждало то, что ниже. Теперь наверху файла лежит `[hidden] { display: none !important }` — атрибут `hidden` это `display:none` из браузерного стиля, и любое авторское правило `display` его перебивает.

QR сканируют телефоном, а браузер, ждущий вход, стоит на другой машине. Отправлять телефон в приложение бессмысленно: пользователь смотрит не туда. auth-center помечает ссылку QR флагом `q` (кнопка — флагом `b`), мини-апп читает флаг из подписанного `start_param` и в случае `q` не просит у auth-center код возврата, а тот его не выписывает.

Кнопки не будет и тогда, когда в сессии не было `redirect` — вести некуда. Логика на странице одна: нет кода — нет кнопки, и тогда страница закрывает себя.

Полторы секунды — потому что эта карточка единственное, что вообще сообщает пользователю об успехе на этом устройстве: вкладка, которая закончит вход, стоит в другой комнате. Меньше — не успеет прочитать имя, больше — начнёт искать крестик.

### Протухшая сессия ведёт в ту же парадную дверь

`auth-center said 409: session already used` и `auth-center said 404: expired` — не поломки. Telegram **возобновляет** оставленный открытым мини-апп вместо запуска нового, поэтому вторая попытка приезжает с той же ссылкой, что и первая: сессия за ней либо уже закрыта первой попыткой (409), либо успела истечь свои пять минут (404). Ссылка протухла, человек — нет: `initData` проверена строчкой выше, иначе до `bindSession` дело бы не дошло.

Поэтому на оба отказа `handleAuth` уходит в `homeLogin` — тот самый вызов, которым обслуживается гость с пустым `start_param`. Пользователь получает то же, что получил бы, открыв мини-апп из меню: код на `MINIAPP_DIRECT_REDIRECT`. В логе это `via=home after=stale session=…`.

Развилка живёт в `spentSession()` и смотрит на статус, а не на текст сообщения — кроме одного места. У 404 текст всё-таки проверяется на `expired`, и намеренно: 404 отвечает **любой** веб-сервер на путь, которого у него нет, так что опечатка в `AUTH_INTERNAL` иначе тихо увела бы каждый вход в домашнее приложение вместо того, куда пользователь шёл. `expired` — собственное слово auth-center (см. `handleMiniappAuth` в его `miniapp.go`), и больше им никто не отвечает. Для 409 такой страховки не нужно: случайных 409 веб-серверы не выдают.

Битая ссылка по-прежнему останавливает вход — но её ловят ветки выше, до всякого обращения к auth-center: обрезанный токен и неизвестный флаг. Баг, заканчивающийся успешным входом, худший из возможных. Если парадная дверь не настроена (auth-center отвечает `503` на `/miniapp/home`), пользователь увидит исходный отказ про сессию, а не отказ нашего запасного пути. Все случаи закреплены тестами в `build/auth_test.go`.

## Парадная дверь (пустой `start_param`)

До сих пор мини-апп был служебным каналом: приложения через него согласовывают вход, а человек в нём не бывает. Но забрести в него можно — из бота, по ссылке `t.me/<bot>/<app>`, через menu button, — и до этой правки такой гость упирался в «в ссылке нет сессии входа».

Отличить его не стоит ничего: логин-ссылка **всегда** несёт `?startapp=<флаг><токен>`, а гость приходит с пустым `start_param`. Развилка живёт здесь, а не в auth-center: `start_param` лежит внутри подписанной `initData`, и проверяет её только этот сервис — auth-center её не видит и видеть не может.

```
пустой start_param
   → POST /miniapp/home {secret, user}       (сессии нет, называть нечего)
   → auth-center: {redirect: <его env>, code}
   → «Вы вошли как: ‹имя›» + кнопка → redirect?code=… → приложение гасит код через /exchange
```

Ответ ручки той же формы, что у обычного входа, и страница не различает эти случаи вовсе — ей приходит имя и один путь наружу. Различают их только логи: `via=home` вместо `via=qr|button`.

**Куда ведёт дверь, решает auth-center**, переменной `MINIAPP_DIRECT_REDIRECT` на его стороне. Здесь новых переменных не появилось ни одной, и это осознанно: общий секрет позволяет этому сервису утверждать личности, чью подпись он проверил, и на этом его полномочия должны заканчиваться. Умей он ещё называть адрес — мог бы направить действительный одноразовый код куда угодно.

**Что в эту дверь не проваливается.** Пустой `start_param` — это гость. А вот `start_param`, который есть, но не разбирается (обрезанный, с неизвестным флагом, с протухшей сессией), по-прежнему честно сообщает об ошибке. Превратить сломанную логин-ссылку в поездку в menu значило бы спрятать реальный сбой от человека, который шёл совсем в другое приложение.

Не задан `MINIAPP_DIRECT_REDIRECT` — auth-center отвечает `503`, гость видит прежнюю ошибку. Фича включается ровно как бот-половина: одной переменной, и её отсутствие — рабочее состояние.

## Бот-половина (`APP_URL`)

Необязательная и полностью отдельная от входа часть: бот, который отвечает на сообщения в личке. Пуст `APP_URL` — этого всего нет: маршрут не регистрируется, к Telegram не уходит ни одного запроса, мини-апп ведёт себя ровно как раньше.

**Что стоит знать перед включением.** До этой ручки auth-miniapp не делал к Telegram ни одного исходящего вызова — он только проверял подписи того, что ему принесли. Именно поэтому `auth-proxy` больше не нужен для входа. Вебхук возвращает зависимость от достижимости `api.telegram.org` с этого хоста. Вход от этого не ломается: `setWebhook` не пройдёт, в логе будет строка, все остальные маршруты продолжат работать — просто бот никому не ответит.

### Регистрация при старте

`APP_URL` — это адрес **самого приложения**, путь `/webhook` дописывается сам (полный URL с путём тоже примут — дублироваться не будет). Переменная поэтому и называется `APP_URL`, а не `WEBHOOK_URL`: она говорит, где живёт сервис, а не какую ручку дёргать, — то же имя и с тем же смыслом используется в auth-client, и следующему, кому понадобится собственный адрес приложения, не придётся заводить вторую переменную. Telegram принимает только https с валидным сертификатом.

```
setWebhook(url=<APP_URL>/webhook,
           secret_token=<случайный, см. ниже>,
           allowed_updates=["message"],
           drop_pending_updates=true)
```

`allowed_updates` — только то, что обрабатывается: правки, реакции и посты каналов приезжали бы, чтобы быть встреченными молчанием. `drop_pending_updates` — накопившееся за время простоя разгребать незачем: приветствие, просроченное на сутки, это шум, а сообщение старше 48 часов Telegram всё равно удалить не даст.

Вызов уходит **в горутине**, не на пути старта: это обращение к третьей стороне, и вход не должен его ждать. `/api/auth` работает с той секунды, как поднялся `ListenAndServe`, независимо от того, взял ли Telegram трубку.

`setWebhook` эксклюзивен: включив это, ты забираешь вебхук у всего, что было зарегистрировано на этого же бота.

### Секрет

Переменной для него нет намеренно. Значение генерируется при старте (32 случайных байта, base64url) и уезжает в том же `setWebhook`, который объявляет URL. Telegram возвращает его в заголовке `X-Telegram-Bot-Api-Secret-Token` на каждом апдейте; всё, что пришло без него, получает `403` и в лог.

Так две стороны не могут разъехаться, и нет credential'а, который можно забыть, утечь или не ротировать — тот же приём, что и с общим секретом auth-center. Плата: два инстанса на одного бота перетирали бы регистрацию друг друга — но это верно и про сам `setWebhook`, с секретом или без.

### Что делает бот

Только в личке. Два исхода:

| Пришло | Что делает | Метод |
|---|---|---|
| `/start` (в том числе `/start <payload>` и `/start@bot`) | отвечает приветствием (константа `greeting` в `webhook.go`) | `sendMessage` |
| что угодно другое — текст, фото, стикер | удаляет сообщение | `deleteMessage` |

`/startgame` — это другая команда, а не `/start`: проверяется, что после префикса идёт конец строки или разделитель. Тест `TestIsStartCommand`.

**Группы не трогаются вообще.** Удаление разрушительно и здесь оно поведение по умолчанию, поэтому оно применяется только там, где правило и задумано — в переписке один на один. Если бота добавят в группу, он промолчит; с правами админа он бы иначе принялся чистить чужие сообщения. Снять guard — одна строка в `handleMessage`, если группа когда-нибудь окажется местом для этого бота.

Удалять чужие сообщения в личке боту можно (Bot API: *bots can delete incoming messages in private chats*), но **не старше 48 часов** — отказ Telegram в этом случае попадает в лог как есть и не ретраится.

### Ответы и ретраи

Telegram повторяет апдейт, пока не получит 2xx. Поэтому `200` отвечает всё, включая нечитаемое: апдейт, который не разобрался один раз, не разберётся и на пятый, а ретрай принесёт только ту же строку в логе. Единственное исключение — несошедшийся секрет: `403` и никаких подсказок о том, что именно не так.

Отвечает ручка **до** работы: Telegram держит следующий апдейт до ответа на текущий, так что вызов Bot API внутри обработчика тормозил бы соседнего пользователя. Сообщение к этому моменту уже скопировано и от запроса не зависит.

### Логи

```
webhook: registered url=https://miniapp.example.com/webhook
webhook: start chat=507717647 — greeted
webhook: deleted chat=507717647 msg=1841
webhook: delete chat=… msg=… failed: deleteMessage: telegram said 400: message can't be deleted
webhook: REJECTED from=1.2.3.4:5678 — secret mismatch
```

Токен бота не попадает в лог никогда: он живёт в URL вызова, а в текст ошибки идёт только имя метода.

## Включение на стороне auth-center

Переключает одна переменная auth-center — `MINIAPP_SHORT_NAME`, short name мини-аппа на том же боте:

```ini
Environment=MINIAPP_SHORT_NAME=direct
```

Задана — и QR, и кнопка «open in telegram» ведут в мини-апп. Пуста — обе ведут на бота, как раньше. Ссылка на сессию одна, поэтому QR и кнопка не могут указывать в разные места.

Откат — снять переменную и перезапустить auth-center. Webhook-путь никуда не делся и продолжает работать; пересобирать ничего не нужно.

Подробности — [auth-center/README.md](/auth-center/README.md), раздел «Переключение Telegram-ветки».
