# auth-miniapp

Telegram-ветка auth-center без бота и без webhook. Мини-апп открывается внутри Telegram, проверяет подпись `initData` по `BOT_TOKEN` и сообщает личность в auth-center — тот привязывает её к сессии, которую браузерная вкладка уже опрашивает на `/poll`.

Вырос из [poc-telegram-app](/poc-telegram-app/README.md), где проверялась сама возможность: подпись сходится, а `start_param` из ссылки покрыт этой подписью.

```
вкладка браузера ──POST /qr-session──> auth-center            (сессия, токен)
       │                                    ▲
       │ ссылка t.me/<bot>/<app>?startapp=<токен>
       ▼                                    │
   Telegram ──> auth-miniapp ──POST /miniapp/auth──┘          (личность → сессия)
       │              (проверка HMAC)
       ▼
  WebApp.close()

вкладка ──GET /poll/{токен}──> code ──> redirect?code=…
```

## Чем отличается от нынешней кнопки «open in telegram»

Сейчас пользователь жмёт кнопку, попадает в чат с ботом, шлёт `/start <токен>`, Telegram доставляет апдейт на `POST /webhook` — напрямую или через [auth-proxy](/auth-proxy/README.md), если VPS не видит Telegram. Личность приезжает из тела апдейта.

С мини-аппом переписки с ботом нет: личность приходит из `initData`, подписанной `BOT_TOKEN`. Webhook и proxy для этой ветки не нужны — исходящий трафик к Telegram не требуется вообще.

Остальная половина протокола не меняется: `/poll`, одноразовый код, `POST /exchange`. Клиентские приложения ничего не заметят — `method` остаётся `telegram`.

## Переменные окружения

| Переменная | Обязательно | Описание |
|---|:---:|---|
| `BOT_TOKEN` | да | Токен бота от @BotFather. **Того же бота, что у auth-center** — из него обе стороны выводят общий секрет. Без токена приложение не стартует |
| `AUTH_INTERNAL` | да | Базовый URL auth-center, без пути. На одном хосте — `http://localhost:8886`, вызов не выходит наружу. На разных — публичный `https://…`, **обязательно https**: в теле запроса едет общий секрет |
| `APP_NAME` | | Имя приложения: баннер `--version` и строка лога `start app=…` |
| `PORT` | | Порт сервера (по умолчанию `8892`) |

`BOT_TOKEN` и `AUTH_INTERNAL` проверяются при старте, а не при первом запросе: приложение, поднявшееся без них, выглядит здоровым и падает ровно в тот момент, когда кто-то пытается войти.

Базы данных нет.

## Маршруты

| Маршрут | Описание |
|---|---|
| `GET /` | Страница мини-аппа |
| `POST /api/auth` | `{"init_data": "<WebApp.initData>"}` → проверка подписи → вызов auth-center |

Ответ:

```json
{"ok": true, "user_id": 507717647, "name": "Сергей Шумилов",
 "username": "sergey_showmelove", "redirect": "https://auth.sh-development.ru/",
 "code": "<одноразовый код>"}
```

`redirect` и `code` — путь назад: адрес приложения плюс код, выписанный **этой странице отдельно**. Кнопка склеивает их в `redirect?code=…` и уводит туда webview.

Код именно второй, не тот, что лежит в сессии: тот ждёт вкладка на `/poll` и потратит его, а одноразовый код, потраченный дважды, у кого-то не сработает. Два кода на одну проверенную личность ничего не раскрывают — каждый одноразовый, каждый живёт 60 секунд, и погасить любой всё равно можно только с `app_token`.

Ошибки — `{"ok": false, "error": "…"}`. Коды: `401` подпись не сошлась, `400` нет `initData` или в ссылке не было сессии, `502` auth-center отказал или недоступен (его формулировка передаётся как есть).

## Доверие между сервисами

auth-miniapp проверяет `initData` сам, значит `BOT_TOKEN` у него уже есть — тот же, что у auth-center. Вместо того чтобы заводить отдельный `APP_TOKEN`, обе стороны выводят из токена одно значение:

```
secret = hex(HMAC_SHA256(key=BOT_TOKEN, data="auth-center/miniapp/v1"))
```

Сам токен по проводу не ходит — это полный доступ к боту, и в теле каждого запроса ему делать нечего. Сравнение через `hmac.Equal`.

Значение выводится независимо с двух сторон и никогда не передаётся, поэтому расхождение никак не проявится в рантайме — auth-center просто ответит `403`, и вход сломается без объяснений. От этого страхует пара тестов с одной и той же фикстурой: `build/authcenter_test.go` здесь и `build/miniapp_test.go` в auth-center. Меняешь строку назначения или способ вывода — один из них падает и называет расхождение.

## Проверка подписи

Алгоритм из [документации Telegram](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app), `build/telegram.go` перенесён из PoC вместе с тестами:

```
secret_key = HMAC_SHA256(key="WebAppData", data=<bot_token>)
hash       = HMAC_SHA256(key=secret_key, data=<data_check_string>)
```

Проверяется и свежесть `auth_date` (не старше 24 часов).

Главное здесь — `start_param`. Значение `?startapp=` из ссылки входит в подписанные данные, поэтому токен сессии нельзя подменить по дороге, не сломав подпись. Тест `TestStartParamIsCoveredByTheSignature`.

```bash
cd build && go test ./...
```

## Локальная разработка

```bash
cd auth-miniapp
cp .env.example .env   # заполнить BOT_TOKEN и AUTH_INTERNAL
docker-compose -f dev-compose.yml up --build
```

Порт `8892`. В обычном браузере страница честно скажет, что не видит Telegram — реально проверять только через Telegram по HTTPS.

## Сборка продакшн-бинаря (linux/amd64)

```bash
cd auth-miniapp
docker-compose -f prod-compose.yml run --rm release
```

Бинарь окажется в `bin/auth-miniapp`.

## Деплой

1. Скопировать `bin/example.auth-miniapp.service` в `/etc/systemd/system/auth-miniapp.service`, заполнить `ExecStart=`, `WorkingDirectory=`, `BOT_TOKEN=`, `AUTH_INTERNAL=`.
2. `systemctl daemon-reload && systemctl enable --now auth-miniapp`
3. nginx на домен мини-аппа → `http://127.0.0.1:8892`, сертификат через certbot. **Telegram открывает мини-аппы только по HTTPS с валидным сертификатом.**
4. @BotFather → `/newapp` на боте auth-center → указать этот домен и `app_short_name`.

## Ссылка

```
https://t.me/<bot>/<app_short_name>?startapp=<токен сессии>
```

Токен сессии — то, что `POST /qr-session` возвращает в поле `token`: 43 символа из `A-Za-z0-9-_`, в `startapp` помещается без кодирования.

Пока кнопка в auth-center на неё не переведена, ссылка собирается руками — см. ниже.

## Проверка цепочки

Сессию можно завести curl'ом и открыть ссылку с полученным токеном:

```bash
TOKEN=$(curl -s -X POST https://auth-center.sh-development.ru/qr-session \
  -H 'Content-Type: application/json' \
  -d '{"redirect":"https://auth-client.sh-development.ru/callback"}' | jq -r .token)

echo "https://t.me/<bot>/<app>?startapp=$TOKEN"

# пока открываешь ссылку в телефоне — смотреть, как сессия меняет статус
watch -n1 "curl -s https://auth-center.sh-development.ru/poll/$TOKEN"
```

Ожидаемое: `pending` → `authenticated` с `code` и `redirect`, в логе auth-miniapp строка `auth: BOUND uid=… session=…`, в логе auth-center — `miniapp uid=…`. Сессия живёт 5 минут.

У страницы ровно два исхода, и оба выглядят как страница входа auth-center: та же палитра, та же карточка, рамка-заголовок сверху и одна большая кнопка под ней — по высоте как плитки выбора провайдера (80 px).

- **вошёл** — «привет, ‹имя›» (нет имени — `@username`, нет и его — `id ‹номер›`), кнопка «назад»;
- **не вошёл** — «не удалось войти» красной рамкой, тихой строкой техническая причина, кнопка «ещё раз».

Цветом окрашен только отказ. Успех не красится в зелёный намеренно: auth-center молчит цветом, пока всё идёт нормально, и зелёная карточка звучала громче оригинала.

Причина отказа не переводится: её читает не пользователь, а тот, кому он пришлёт скриншот. Закрыть мини-апп можно крестиком самого Telegram, своей кнопки для этого нет.

### Куда ведёт «назад»

Зависит от клиента — `WebApp.platform`:

| Клиент | Куда | Почему |
|---|---|---|
| `tdesktop`, `macos`, `weba`, `webk`, `web` | внешний браузер, `WebApp.openLink()` | у пользователя приложение уже открыто в настоящем браузере; оставить его во встроенном — значит развести две копии по двум местам |
| всё остальное | этот же webview, `location.href` | телефон уже внутри Telegram, и `openLink` выбросил бы его в Safari или Chrome — наружу из приложения, откуда он пришёл |

Деление именно «десктоп против всего остального», а не «десктоп против мобильных»: неизвестная платформа скорее окажется новым мобильным клиентом, чем новым десктопным, и ошибка в эту сторону ничего не стоит — ссылка, открытая на месте, работает всегда.

Страница сама не закрывается. Закрыть её молча, оставив пользователя перед свёрнутой вкладкой, — это ровно то, чего он не понимает.

Кнопка меняет `location` самого webview, а **не** зовёт `WebApp.openLink()`. `openLink` по документации Telegram открывает внешний браузер — и открывает: пользователь оказывается в Safari или Chrome, вообще за пределами Telegram. Это хуже свёрнутой вкладки, которую кнопка чинит. Навигация webview — единственный способ остаться внутри.

Плата за это: webview мини-аппа может не разделять куки с встроенным браузером, поэтому на сессию, которую только что завела вкладка, полагаться нельзя. Ровно поэтому в ссылке едет собственный код — приложение залогинит пользователя на входе, независимо от кук.

## Включение на стороне auth-center

Переключает одна переменная auth-center — `MINIAPP_SHORT_NAME`, short name мини-аппа на том же боте:

```ini
Environment=MINIAPP_SHORT_NAME=direct
```

Задана — и QR, и кнопка «open in telegram» ведут в мини-апп. Пуста — обе ведут на бота, как раньше. Ссылка на сессию одна, поэтому QR и кнопка не могут указывать в разные места.

Откат — снять переменную и перезапустить auth-center. Webhook-путь никуда не делся и продолжает работать; пересобирать ничего не нужно.

Подробности — [auth-center/README.md](/auth-center/README.md), раздел «Переключение Telegram-ветки».
